## The base rate, and why it breaks comparability

At **0.12908%** this anchor sits **31x below** the synthetic default's
measured **4.03%**.

That is more than an order of magnitude, so the two are not comparable and no operating point carries across. A 1% FPR here buys 63,626 false positives against 8,213 fraud rows, so precision@k collapses in a way it never does on synthetic traffic. Thresholds must be set at this rate, and synthetic numbers never share a table with these.

**The split shifts the rate again.** Fraud is 3.5x denser in the test half (0.28898%) than in the train half (0.08162%). This is a property of the data, not of the cut: the label is spread near-uniformly across steps while the legit volume is not, so any chronological boundary lands on two different base rates. A threshold calibrated on a held-out slice of train does not transfer unchanged to test, and a recall figure has to name which side it was measured on.

`artifacts/splits/paysim_oot.json` on every run. The boundary is two timestamps, so the
partition is identical whatever subset of rows is loaded.

**Embargo rationale.** Velocity features look back up to 24h. A 24-step embargo stops a test row's features being computed over train-side rows, and stops a fraud ring straddling the boundary.

## Sampling

The loader keeps a deterministic **10% hash-sample of `nameDest`** — 636,409 rows, 803 fraud, base rate 0.12618% against the full file's 0.12908% (-2.2% relative). Whole entities are kept or dropped, never individual rows, so every kept entity still has its complete history and the time span is unchanged. Set `data.sample.sample_fraction=1.0` to read the lot — it costs about 10x the memory.

## Data integrity

Counted from the file, not assumed. The loader clamps a non-positive amount to 0.01 and logs the
count rather than dropping the row, because dropping rows silently moves the base rate.

## Quirks

- nameOrig is effectively unique per row: 6,353,307 distinct origins over 6,362,620 rows (mean 1.001 txns each, max 3). There is NO sender history in PaySim. Every src-side velocity, RFM and recency feature is structurally empty on this anchor; the only entity with a past is nameDest (mean 2.34 txns, max 113). Ticket 07's feature set has to be built on the beneficiary side or it is building on nothing.
- Traffic is violently non-uniform across steps: 341 of the 743 steps carry under 100 rows, while step 19 alone carries 51,352. Cutting the split at 67% of the STEPS puts 95.3% of the rows in train and leaves a 4% test tail, so the boundary is derived from the row quantile instead.
- Fraud only in TRANSFER / CASH_OUT.
- Balance columns are a generation artifact (leak); see balance_policy.
- isFlaggedFraud fires on 16 rows out of 6.36M. It is a naive rule, not ground truth.
- 16 rows carry amount == 0, which the contract rejects. The loader clamps them to 0.01 and logs the count; dropping them instead would move the base rate in silence.
- No self-transfers (src == dst) anywhere in the file.

## What it cannot tell us

- Nothing about card rails, UPI or agentic commerce; those enter only via injected vectors.
- No merchant category, no geo, no device. Device features are unmeasurable on this anchor.
- Base rate 0.129% is ~130x below the synthetic default, so operating points set on synthetic traffic do not carry over. See docs/adr/0002-dataset-anchors.md.
